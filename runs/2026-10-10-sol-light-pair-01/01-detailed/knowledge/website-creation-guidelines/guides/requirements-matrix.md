# Requirements coverage matrix

This guide maps the library across three dimensions: **subject x library role x implementation objective**. A subject identifies the concern, a [library role](../README.md#library-abstractions) identifies the material's responsibility, and an implementation objective states what has to be implemented. The ten subject categories and the objective categories below are a working classification. This index adds no website requirements or project deliverables.

## Reading the matrix

- The subject-role view uses rows for subjects and columns for source/support roles. The objective view provides another way to select relevant subjects and role-specific material. These are views of the same three-dimensional matrix.
- Objectives can span subjects: implementing an enquiry flow may concern functionality, interaction, privacy and operations. One source can apply to several objectives without being copied.
- Every numbered rule has one authoritative definition under `rules/`. Capability contracts select those definitions and supply inputs and verification cases; guides explain them; workflows apply them; templates structure the resulting project records.
- One rule may be referenced by several subjects without being copied or assigned a new ID. Folder placement does not make subject classification exclusive.
- An empty cell does not automatically mean missing documentation. Add material when it resolves a concrete need, not to fill every intersection.
- Sources establish provenance. Their presence or detail is not a measure of requirement coverage or implementation quality.

Project records use the [brief](../templates/project-brief.md), [decision register](../templates/decision-register.md) and [acceptance report](../templates/acceptance-report.md). Implementation details can remain in the target project's existing documentation, linked from the brief.

[Compilation](../compilation/README.md) spans all ten subjects. Its [workflow](../compilation/compile-implementation-units.md) combines project inputs, knowledge and selected procedures into the chosen solution structure, all [implementation units](../compilation/implementation-unit.md) and a complete [plan](../compilation/implementation-plan.md) before execution. [Implementation](../implementation/README.md) executes the accepted package under the supplied policy and produces outputs and evidence. Both stages have their own guide, procedure and record formats while referencing the source/support roles shown here.

Concrete objectives belong in the brief; objective-to-structure-to-unit mappings belong in the plan; rule/requirement coverage and actual evidence belong in the acceptance report or existing linked records. This library matrix is a source-navigation view, not project coverage evidence.

Rules, workflows and templates address these subjects broadly; explanatory guides concentrate on architecture and implementation. [Accounts, commerce and booking](../capabilities/extensions.md) have extension requirements rather than complete reusable capability contracts.

## Provenance links

- **R** points to the retrospective origin statement for the initial library. It is broad provenance, not a source map for every individual rule or matrix entry.
- **W** points to Wapps notes identifying imported documents, retained concepts, destinations and deliberate adaptations. Those notes distinguish reusable guidance from source-project implementation facts.

A source label does not establish that every item in the row came from that source. More specific provenance belongs with the relevant rule or guide when evidence is available.

## Applicability and evidence across all subjects

Subject, role and objective remain separate from applicability, decision status and verification outcome. The brief selects objectives, capabilities and execution policy; the decision register distinguishes requirements, accepted defaults, proposals, assumptions and exceptions; implementation notes distinguish planned structure from inspected facts. Units define bounded work on structural elements, the plan records the full package and its acceptance, execution records capture progress, and the acceptance report separates planned coverage from actual evidence.

The [QA rules](../rules/verification.md) apply across the matrix. Outcomes remain `pass`, `fail`, `not checked` or `not applicable` with a reason. The acceptance report's [representative state matrix](../templates/acceptance-report.md#representative-state-matrix) covers relevant viewport, input, content, appearance, operation, navigation, dependency, persistence, visibility and privacy conditions.

## Example relationship

An illustrative objective is "implement enquiry submission to the selected receiver". The brief states this objective, the receiver and required outcome. [FORM-03](../rules/capabilities/forms.md#form-03), selected by the [Forms capability](../capabilities/forms.md), concerns functional behaviour and operations. [Architecture guidance](architecture.md#dependency-direction-and-composition) explains the integration boundary, and the [feature workflow](../workflows/add-page-or-feature.md) supplies implementation and verification actions.

Compilation might map the objective to a form component, submission module and receiver adapter in the chosen solution structure, then define units to create, integrate and verify those elements. This is an illustrative partition, not a required architecture. The plan binds the units, dependencies and delivery checkpoint upfront. Execution produces artifacts and evidence; the acceptance report links the confirmed receiver outcome to the rule, objective, plan/unit revisions and checked implementation version. Provenance stays linked at the scope supported by the source notes.

This relationship gives one rule several useful views while keeping its definition and project evidence in their authoritative locations.
